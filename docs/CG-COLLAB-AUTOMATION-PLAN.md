## 触发和执行

1. GitHub Issue 是派单入口。首选 Codex 桌面定时检查固定仓库中的候选任务。新 Issue 进入候选队列，只有授权人的批准记录与任务范围及内容版本匹配，才会在下一次检查被领取。使用本地项目时需要电脑与桌面应用在线。参见 [Codex 定时任务](https://learn.chatgpt.com/docs/automations)。
2. 若未来需要事件触发，可用 GitHub Actions 的 issues 事件或 Webhook。issues 工作流须存在于默认分支，启用另行审批。Actions 本身负责事件和检查，Codex 仍需明确配置执行入口与凭证。Webhook 需要受管接收端、签名校验和投递去重，之后由受控执行器启动 Codex。参见 [GitHub Actions 事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issues)、[Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)和[Webhook 签名](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)。
3. 固定仓库、批准人、阶段、允许操作、依赖与验收条件。将批准绑定 Issue 内容版本。领取前复核批准仍有效、依赖通过、基线符合预期。运行只在指定隔离目录进行，任务内容和附件视为不可信输入。
4. 同阶段按依赖顺序串行处理，每次运行限定任务数和时长。完成当前任务后重新核对下一条批准及依赖。到达阶段验收点、任务阻塞或涉及重大操作时停止。

## 报告、通知与去重

- 每项报告记录任务编号、执行分支、基线与提交 SHA、修改文件、测试结果和退出码、实际证据、未解决问题、风险。标注模拟、本机、隔离或生产。公开仓库仅放脱敏摘要。
- 第一轮自动生成本地报告，沿用已有授权会话按次回填。未来若另行批准自动写回，专用身份仅在指定仓库具备必要 Issues 写入权限，禁止代码写入和部署。将脱敏结果写到原 Issue，附固定报告引用。00 号独立读取并标为 PASS、PARTIAL、BLOCKED 或 NEEDS HUMAN。
- 完成或阻塞可在同一 Issue 通知 00 号，首次验证要求收件侧证据。现有 22:00 汇总可作后备通道。阻塞报告包含失败点、受影响步骤和所需决定。涉及创始人批准的事项停止执行并提示。
- 用仓库、Issue 编号、批准版本生成唯一键，领取时持有原子锁。记录领取、执行、报告和回传状态。重启先核对报告及远程回传标记，再继续。只重试明确的临时失败。忽略自身评论和结果事件，限制并发、重试次数与运行时长。报告失败只重试回传，避免重复执行。

## 权限、成本和风险

- 首轮沿用 GitHub 只读连接和现有电脑，新增付费 API 和第三方服务支出为零。Codex 定时运行仍占账户用量，首轮实测后再决定频率。事件方案的运行器、模型及托管费用需另算。
- 当前不扩大权限。正式部署、资金、数据库迁移、真实客户数据和重大业务规则由创始人单独审批。执行器不得持有生产部署或生产数据库凭证。
- 风险包括未批准 Issue 注入指令、重复处理、报告泄露、离线错过调度和通知未达。分别通过结构化批准校验、持久化去重、脱敏及收件侧回执处理。只有日志能证明定时触发时，才记录自动触发通过。
